03 / Math / Algorithm Used

Math / Algorithm Used

Grid: strike ∈ {1100, 1150, ..., 1450} VND/kWh (8 values), ratio ∈ {0.70, 0.80, ..., 1.30} (7 values, contracted volume as a fraction of the S1 load of 5,000,000 kWh/month).

Escalation (n = 1..20 years): retailn = retail1 × 1.04n-1, striken = strike × 1.04n-1, fmpn = fmp1 × 1.04n-1. Service and clearing fees do not escalate (constants, per the plan's spec).

Per year: billn = buildFiveLineBill({fmp: fmpn, strikePrice: striken, retailTariff: retailn, ...fixed fees/loss factors}, {contracted, total: load}) — the exact same engine call the app itself uses.

Gates: buyer = ∑n=1..20 12 × cKhn ≤ ∑n=1..20 12 × load × retailn; lender = strike ≥ 1,380 (illustrative 1.2× DSCR proxy on a 1,150 VND/kWh debt-service baseline); investor = strike ≥ 1,450 (illustrative full-LCOE proxy). allPass requires all three.

Self-check: the anchor cell (strike=1250, ratio=1.00, year 1) must reproduce cKh = 9,063,196,000 VND exactly, matching spine-s1.json byte-for-byte — the script exits non-zero if this drifts, catching any future divergence between the sweep's inputs and the canonical spine pack.

06 / Limitations / Second-Best Alternative

Limitations / Second-Best Alternative

  • The lender and investor gates use illustrative per-kWh proxy constants (1,380 VND/kWh debt-service threshold, 1,450 VND/kWh full-LCOE threshold) rather than a true debt-schedule/equity-IRR model, because settlement.js is deliberately buyer-side only (CON-001 in the plan forbids changing its numeric behavior). This is documented plainly in gate-sweep.json's meta.note field and labeled "illustrative" wherever it surfaces.
  • Second-best alternative (rejected, per the plan's ALT-002): build a true developer-side DSCR/IRR model with debt schedules and capex. Rejected for this phase — out of scope for a buyer-side settlement engine and unnecessary for the teaching point, which is the trade-off shape, not precise developer financing terms.
  • The buyer/lender/investor gates are evaluated independently per cell; the lender and investor gates depend only on the strike axis (not the ratio axis), which is why the heatmap's teal region forms a clean vertical band rather than an irregular shape — this is a direct, correct consequence of the proxy formulas, not a rendering artifact.
07 / Errors / Warnings / Flags

Errors / Warnings / Flags Encountered

  • Real bug found and fixed: node scripts/export-sweep.mjs initially failed with ERR_MODULE_NOT_FOUND for ./profiles — settlement.js's import lacked a file extension, which Vite's resolver tolerates but Node's native ESM loader does not. Confirmed the pre-existing export-spine.mjs had the identical latent problem (never actually verified runnable via plain node before this session). Fixed at the root cause: added the .js extension to the one import line in settlement.js. Re-verified: both export scripts run with plain node, the app still builds identically (same bundle size), and all 51 unit + 27 e2e tests still pass.
  • Self-caught orientation bug: the first heatmap render swapped the strike/ratio axes relative to the pre-existing axis-label text keys (m5_xlabel said "Strike price scenarios" but strikes were plotted on the y-axis). Caught by visually inspecting the rendered PNG before moving on; fixed by transposing the grid construction so x=strike, y=contracted-volume ratio, matching the existing labels. Re-rendered and re-inspected to confirm.
  • No test failures, lint errors, or build failures encountered after both fixes.
