Phase 1–2: Deploy Recovery & Freshness Guardrails

The first two phases of a five-phase plan to close what a fresh repo review found outside the DPPA teaching case's already-hardened number pipeline: a stale production deploy, a mislabeled release tag, and no mechanism to notice either drifting again.

The live demo site at dppa-case.web.app — the URL on the teaching deck's closing-slide QR code — had been serving software from before the entire October redesign for 18 commits. It is now redeployed from current master, correctly tagged, and every future build embeds a verifiable commit marker that two new scheduled checks compare against reality every week, with no proprietary tooling and no new credentials required.

01 / Executive Summary

Executive Summary

What changed

  • Deploy recovered. https://dppa-case.web.app was redeployed from the current master tip, bringing in 18 commits of work — the entire October Modules 1–6 teaching-revamp, the readiness-hardening arc, and the prose-parity number-pipeline hardening — that had never reached the live site.
  • Release tag corrected. The existing v1.0-oct-workshop tag predates the October redesign despite its name; a new tag, v1.1-oct-workshop-hardened, now marks the commit that actually contains October-workshop content. The old tag was left in place (not force-moved) to avoid rewriting a pushed ref.
  • MISSION.md corrected. The project's own north-star document still described the July 2026 session as upcoming; it has already happened (and is the session that exposed the symbol-overload failure the whole October rebuild responds to).
  • Drift is now self-detecting. Every future build embeds a build-commit marker; two new stdlib Python checkers and a weekly scheduled GitHub Actions workflow compare the live site against master and watch the project's human-blocked-deadline register, so this specific class of silent drift cannot recur unnoticed.

Why it matters

A repo can have a rigorously verified number pipeline (deck ↔ engine ↔ prose, already CI-gated by earlier work) and still fail its actual purpose if the artifact people are directed to is stale. The QR code on the teaching deck's closing slide points at this URL; anyone scanning it before this fix would have reached a build with no teach-mode banner, no gate-sweep heatmap, and none of the fixes the October rebuild exists to deliver. This work closes that specific gap and, more durably, removes the dependency on anyone remembering to check it again before the real session.

02 / Background & Objective

Background & Objective

The repo teaches Vietnam's Direct Power Purchase Agreement (DPPA) settlement mechanics through a live web app, a slide deck, facilitator guides, and printed handouts. A prior hardening arc (documented in plans/2026-07-17-prose-parity-second-pipeline-plan.md) made the deck's figures trustworthy: the settlement engine computes every number, JSON exports are the interface, and CI regenerates and diffs them. A follow-up repo review on 2026-07-21 deliberately looked outside that already-hardened territory and found the opposite kind of gap: the live demo tool and its release tag were both frozen at a pre-redesign commit from 2026-07-05, CI was silent on visual regressions and accessibility, root-level files had drifted into unsorted clutter, and a documentation gap had been flagged by three separate analysis passes without ever being closed (research/2026-07-21-deploy-drift-and-repo-hygiene-brainstorm.md).

The resulting five-phase plan (plans/2026-07-21-deploy-drift-repo-hygiene-plan.md) sequences that work by consequence and effort: fix what's live and stale first, then make that fix durable with automated guardrails, then close CI rigor gaps, then declutter, then document. This report covers execution of the first two phases — deploy recovery and the freshness guardrails — which together were judged the highest-consequence, lowest-effort work in the plan.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding assumptions applied

  • Firebase CLI authentication on the executing machine was assumed already valid (per the plan's ASM-001); confirmed true — npx firebase projects:list showed dppa-case already accessible, no interactive login was needed.
  • The existing v1.0-oct-workshop tag was not deleted or force-moved (ASM-003) — a new tag was created instead, matching this repo's established non-destructive convention (git mv over rm elsewhere in the repo).
  • Calendar-based drift reminders were implemented as a scheduled GitHub Actions workflow rather than any proprietary scheduling primitive (DEC-002), so the guardrail requires no new infrastructure or credentials beyond what this repo's CI already uses.

Constraints and environment notes

  • New Python tooling is stdlib-only — no requirements.txt exists in this repo (CON-001).
  • check_deploy_freshness.py must never hard-fail on network unreachability, only on a confirmed reachable-but-stale deploy (CON-002) — verified by design, not yet by a live network-outage drill.
  • Local Playwright execution on this Windows machine required --workers=1 for the WebKit project to avoid CPU-contention timeouts during browser launch — a pre-existing, already-documented environment characteristic (app/deployment.md's notes on parallel-worker contention), not a regression introduced by this work.
  • The scheduled workflow's weekly cadence (Monday 09:00 UTC) has not yet had its first real scheduled firing observed — it was validated via YAML-parse correctness and the underlying scripts' local dry runs, not an actual cron trigger.
05 / Methodology

Methodology

Each phase followed the plan's own gate: implement, run the closest available check (lint, full unit suite, full e2e suite, build), fix anything red before committing, and verify the specific outcome the phase claims (a live deploy actually serving new content; a freshness checker actually reporting PASS against a real deployed marker) rather than trusting that "the code looks right." Where a first run surfaced a false signal — the WebKit e2e timeouts turned out to be a local browser-binary/version mismatch, not a real regression — the investigation traced it to root cause (a stale Playwright browser cache) before concluding the suite was clean, rather than working around it silently.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Deploy Recovery & Mission Framing Fix done

Corrected MISSION.md's stale "upcoming July 2026" framing to reflect that the session already happened and exposed the symbol-overload failure the whole redesign responds to. Phase 2 — Deploy & Human-Blocked-Register Freshness Guardrails done

Added a small Vite plugin that injects a <meta name="build-commit"> tag into every built index.html, making the deployed bundle's origin commit mechanically verifiable. Rebuilt and redeployed so the live site actually carries the marker. Built two stdlib-only Python checkers — check_deploy_freshness.py (compares the live marker against local git HEAD, failing soft on network errors) and check_human_blocked_register.py (classifies each readiness-checklist deadline as OK / due-soon / overdue) — following the exact style convention of the repo's existing tools/check_retired_figures.py. Wired both into a new weekly-scheduled GitHub Actions workflow (.github/workflows/freshness-checks.yml), also manually triggerable. A failing scheduled run uses GitHub's own default notification mechanism — no new infrastructure.

Phase 3 — CI Rigor Hardening not started

Bootstrap real Linux visual-regression baselines (currently continue-on-error: true and structurally unable to fail CI), add an @axe-core/playwright accessibility gate, and add Vitest coverage reporting. Scoped and sequenced in the governing plan; not attempted in this session.

Phase 4 & 5 — Repo Hygiene and the Missing Learning Record not started

Phase 4 archives 12 one-off root scripts and 6 orphaned deck/screenshot files into archive/ via non-destructive git mv. Phase 5 writes learning-records/0005, synthesizing the July symbol-overload failure through the October redesign and hardening arc — a documentation gap three separate prior analysis passes have flagged without any of them closing it. 07 / Findings & Recommendation

Findings & Recommendation

Finding 1. The live demo tool was not merely "a bit behind" — it was missing the entire body of work the October redesign exists to deliver (teach mode, the gate-sweep heatmap, the QR code flow, translation scaffolding). A number-pipeline CI gate proving the deck's figures are correct provides no protection against the separate failure mode of the deployed artifact itself being stale; these are orthogonal risks and this repo previously only guarded one of them.

Finding 2. The gap had a social-contract dimension, not just a technical one: the release tag v1.0-oct-workshop would have actively misled a future reader (including a future coding session) into believing October content was already tagged and shipped. Naming a tag after content it doesn't yet contain is a worse failure mode than having no tag at all.

Finding 3. Both new checkers were validated against real, not synthetic, end states before being trusted: check_deploy_freshness.py was run against the actual live site both before the marker existed (correctly reporting UNKNOWN, not a false failure) and after the redeploy (reporting PASS against the real deployed commit). check_human_blocked_register.py was run against the real checklist file, not just its unit-test fixtures, and correctly classified all five register items as OK.

Recommendation. Proceed to Phase 3 next — it is independent of Phases 1 and 2 (per the plan's dependency table) and closes the remaining CI-rigor gaps (toothless visual regression, no accessibility testing) while the deploy-freshness guardrail from Phase 2 is still fresh context. Phases 4 and 5 can run in parallel with Phase 3 or with each other, since none of the remaining phases depend on one another.

09 / Risks / Open Questions

Risks / Open Questions

Risks

  • GitHub's default notification for a failed scheduled workflow goes by email to repo watchers, which the sole maintainer may not check as promptly as a chat alert — acknowledged as a known limitation in the governing plan (RISK-02-01), not addressed in this session.
  • The deploy-freshness checker compares raw commit hashes, not app-content hashes — a future commit that touches only non-app files (docs, other tooling) will make the checker report a one-commit "STALE" finding even though the deployed app bundle is unchanged. This is a known, accepted simplification (matching the plan's Specification exactly), not a defect, but a future reader should not be surprised by it.
  • The scheduled workflow has not yet had a real weekly firing observed end-to-end; only local dry runs and YAML-parse validation have occurred so far.

Open questions

  • Phases 3–5 of the governing plan remain unexecuted; none of their exit criteria have been checked in this session.
  • The human-blocked register's earliest deadline (H1, confirm session date, needed by 2026-08-15) remains open as of this report — unaffected by this session's work, but worth tracking as the date approaches, which is now exactly what Phase 2's new weekly check does automatically.
