## Design Decisions

### Why `<ol class="flow-diagram">` instead of `<div>`
Semantic ordered list reinforces the "step-by-step flow" mental model for screen readers and matches the existing UI patterns (the walkthrough cases already use `<ol>`). Plus `role="list"` is explicit for older browser fallbacks.

### Why `flex: 1 1 100%` on `.flow-row` instead of `display: grid`
Flexbox lets each row auto-wrap nodes when content is wide. The original mermaid SVG was a fixed LR layout that didn't wrap; the new HTML flex layout wraps gracefully. This was the key fix for the mobile horizontal scroll problem (GAP-04).

### Why per-node color tokens (`.flow-node-bau`, `.flow-node-evn`, etc.)
The original mermaid SVG had hardcoded colors in the definition. By moving the colors to CSS classes keyed on semantic node types (BAU, EVN, cancel, developer, keep, dppa, savings), the visual hierarchy is now editable in one place and respects the existing neon color palette (cyan, mint, amber, magenta).

### Why rotate the arrow 90° on mobile
A horizontal `→` between vertically stacked nodes looks broken. Rotating the arrow to a downward `↓` (or right-pointing rotated to point down) signals the flow direction the same way a top-down flowchart would.

### Why keep the `cancellation-flow` class on the container div
The old `#cancellationMermaid` ID is kept (to avoid rewriting all the test selectors and the CSS), but a semantic class `cancellation-flow` is added so future CSS can target it without using a `<div id="...">` selector.

- **RISK-01-01** (HTML/CSS flow diagram less polished than mermaid SVG) — mitigated: using existing neon CSS variables + per-node color tokens + box-shadow effects produces a consistent look. The mermaid diagrams were already small text in compressed boxes; HTML version is more readable.
- **RISK-01-02** (mermaid removal breaks something subtle) — mitigated: grep confirmed mermaid is only used in `main.js` and `ui.js`. Tests cover both render paths. After removal, 38/38 tests pass and build is clean.
