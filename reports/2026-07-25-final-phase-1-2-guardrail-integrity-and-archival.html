01 / Executive Summary

Executive Summary

What was wrong

The live teaching app at https://dppa-case.web.app — the URL on the deck's closing QR code — served a build whose embedded provenance marker named a commit (e55319e) whose own source tree contained no code capable of producing that marker. The deploy had been made from an uncommitted working tree, so the "which commit is live" signal corresponded to no reviewable commit. Separately, the automated weekly freshness check compared that marker against git rev-parse HEAD, meaning any commit at all — including a documentation-only one — would report the site as stale on its first scheduled run.

What was fixed

Phase 1 replaced the marker with a dirty-tree-aware version and replaced the freshness comparison with a content-hash comparison of the live site's actual JavaScript/CSS asset filenames against a fresh local build — immune to a wrong, missing, or dirty marker. The app was rebuilt and redeployed three times in sequence while iterating to a genuinely clean, verified result; the release tag was moved to the deployed commit. Phase 2 found and archived a live landmine: build_callouts.py, a script indistinguishable at a glance from six still-run scripts, still hard-coded the retired figure "0 of 56" at 48pt bold red — the repo's number-accuracy guard had never scanned generator scripts, only the prose they produce.

02 / Background & Objective

Background & Objective

This repository builds and maintains a teaching case for Vietnam's synthetic Direct Power Purchase Agreement (DPPA) mechanism: a source PowerPoint deck, a settlement-math engine, a live browser app used as a presenter's demo aid, and a pipeline of Python/Node scripts and CI checks that keep every number across the deck, app, and worksheets in agreement. A 2026-07-25 research pass (research/2026-07-25-guardrail-integrity-and-audience-localization-brainstorm.md) found that the freshness guardrail built three days earlier — itself meant to make "is the live site current" a checkable fact instead of something someone has to remember — was reporting an answer that could not be true, and was about to fire a false alarm on its first scheduled run.

The resulting six-phase plan (plans/2026-07-25-guardrail-integrity-and-localization-plan.md) scoped that fix (Phase 1) alongside five further hardening and localization phases. This report covers execution of the first two: making deploy provenance honest (Phase 1) and closing the generator-side blind spot in the repo's figure-accuracy guard plus archiving stale scripts and binaries (Phase 2). Both were explicitly scoped as parallelizable and lowest-risk-highest-consequence — the objective was to land them before the next scheduled freshness-check run and well ahead of the 2026-09-15 English content freeze that governs the rest of the plan.

04 / Assumptions & Constraints

Assumptions & Constraints

Assumptions that held

  • ASM-001 (plan): the Firebase CLI would already be authenticated on the executing machine. Confirmed true — three consecutive deploys succeeded without any credential prompt.
  • CON-001 (plan): the committed engine exports must stay byte-identical throughout. Verified after Phase 2's archival with a clean git diff --exit-code against regenerated spine-s1/s2/s3.json and gate-sweep.json.

Constraints and a mid-execution correction

  • The plan's own asset-comparison design (S2) assumed a straightforward glob match on Firebase Hosting's header rules would target /index.html. In execution this needed one iteration: **/*.html and then /index.html + /**/*.html both failed to match the root path the SPA rewrite actually serves; the working fix uses a broad ** rule overridden by a more specific /assets/** rule later in the list, per Firebase's documented same-key-override behavior. Verified live via curl before proceeding.
  • The new generator-scanning guard caught its own documentation: a NOTES.md sentence describing the fixed bug quoted the literal retired string and tripped the guard it was describing. Rephrased to reference the finding without repeating the retired literal — a small but genuine proof that the guard works as designed.
05 / Methodology

Methodology

Each phase followed the same discipline: implement the change, run the closest available verification (unit tests, lint, production build, functional end-to-end tests, and the repo's own Python checker suite), fix anything red before committing, and commit only once green. Where a task changed what the public production site serves — every task in Phase 1 — the change was verified against the live URL directly (curl for headers and content, the rewritten freshness checker for asset-hash equality) rather than trusted from a local build alone. Two iterations inside Phase 1 (the cache-header glob, and a stale local dist/ build that predated a commit) were caught by this live-verification step rather than assumed away, and both were corrected before moving on.

Phase 2 added a directory-exclusion design (test fixtures and the archive itself must not trip the new generator scan) verified with five new unit tests before being run against the real repository, which is what surfaced the build_callouts.py finding as a real, reproducible failure rather than a hypothetical one.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Deploy Provenance & Freshness Integrity

app/vite.config.js's build-commit marker now appends -dirty whenever git status --porcelain is non-empty at build time, so it can no longer claim a bare commit hash for a build that doesn't match one. tools/check_deploy_freshness.py was rewritten: instead of comparing the marker to HEAD, it now builds the current tree locally and compares the live site's content-hashed /assets/* filenames against that fresh build's — a comparison immune to a wrong, missing, or dirty marker, and one a documentation-only commit cannot trip, because it never changes any asset's hash. A live -dirty marker is still a hard failure regardless of matching assets. app/firebase.json now serves no-cache on HTML and a one-year immutable cache on hashed assets. A stray personal name in the app's header ("Rob — Vietnam synthetic DPPA") was removed. The app was deployed three times in sequence while converging on a genuinely clean result, and the release tag v1.1-oct-workshop-hardened was moved (force-push, by design — the old target was already documented as misleading) to the final, freshness-verified commit.

Phase 2 — Generator-Side Guard, Archival & Repo Weight

tools/retired_figures.json gained a scanScripts pattern list (root *.py/*.js, tools/*.py, app/scripts/*.mjs), and tools/check_retired_figures.py now scans it, excluding tools/tests/, archive/, node_modules/, and .git/. Run before archival, it immediately failed on build_callouts.py (three hits, including the 48pt-bold-red slide text) — confirming the finding the brainstorm had only inferred from a static grep. Twelve one-off scripts and seven orphaned binaries (three unused decks, a stale reference deck, two manual-QA screenshots, and the build brief describing them) were moved into a new archive/ directory via git mv, with a README documenting each file's original purpose and live equivalent, if any. The six still-live scripts each gained a one-line header naming what runs them. Three files under the gitignored background/ directory that had been tracked anyway were untracked (kept on disk). The repository was then packed with git gc --aggressive --prune=now.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the original freshness check would have false-alarmed on its very next scheduled run. Comparing a marker to HEAD meant the Monday-morning scheduled workflow (.github/workflows/freshness-checks.yml) was guaranteed to report the site stale after any commit, including a report file. The asset-hash design adopted instead only reports stale when the served bytes actually differ, which is the property that was actually wanted.

Finding 2 — "the app content is current" and "the app's provenance metadata is trustworthy" are different claims, and only the first was true before this work. The served JavaScript bundle was already byte-identical to a fresh build at HEAD before Phase 1 began; the danger was entirely in the unfalsifiable marker, not stale content. This distinction shaped the fix: rebuild trust in the signal rather than treat it as a content emergency.

Finding 3 — a generator script, not just prose, can silently reintroduce a retired number. build_callouts.py sat at the repo root, indistinguishable from six still-run scripts, and would have rendered "0 of 56" (the pre-gate-sweep placeholder) onto a financing-summary slide the next time anyone ran it. The existing guard only ever scanned the documents a build script produces, never the script itself.

Recommendation: proceed to Phase 3 (trilingual app) next, ahead of Phases 4–6. It is the only remaining phase gated by an external deadline — the translator engagement referenced in the plan needs the app's string inventory to brief against, and English content changes must land before the 2026-09-15 freeze. Phases 4 (offline resilience), 5 (CI gate hardening), and 6 (style/documentation unification, which explicitly depends on Phase 3 landing first) do not carry the same deadline pressure and can follow in either order.
