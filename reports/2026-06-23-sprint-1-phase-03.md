## Design Decisions

### Why `@media (hover: hover)` wrapping instead of media query replacement
Wrapping the existing `:hover` rules in `@media (hover: hover)` keeps the desktop hover behavior exactly as it was, while making the active state the primary feedback signal on touch devices. This is the standard pattern from the [WebKit/Chromium blog post on hover media query](https://web.dev/articles/@media/hover).

### Why use `box-shadow` (not `outline`) for `:active`
`:active` feedback should be in addition to the button's normal visual state. A box-shadow is additive (the button still has its own border), while an outline is a separate visual element. A 24px cyan glow on tap is more "tactile" than a 2px outline.

### Why `filter: brightness(1.08)` for walkthrough card
The card already has a complex `background: linear-gradient(...)` and `outline: 2px solid rgba(255,255,255,0.5)`. A brightness filter is a single property that doesn't fight any of the existing visual layers.

### Why `cursor: pointer` on top of `button { cursor: pointer; }`
The plan specifies "scenario-tab and toggle-button if not already present (it's only on `button` generically at line 43)." The class-specific rule is redundant with the generic `button` rule but it documents intent — anyone editing the file later sees the explicit intent.

## Risk Assessment
- **RISK-03-01** (`@media (hover: hover)` breaks hover on hybrid devices like Surface, iPad with keyboard) — mitigated: the new `:active` rules work on all devices regardless of the media query, so touch + keyboard users still get feedback. The only loss is on hybrid devices that DO have a mouse but the OS reports `hover: none` — extremely rare edge case.
