## Design Decisions

### Why `matchMedia('(max-width: 520px)')` instead of hardcoded narrow radius
The chart is a one-time setup, but the viewport can change (window resize, orientation change). Using `matchMedia` makes the detection consistent with the existing `@media (max-width: 520px)` CSS rules. Tradeoff: the radius is set once at chart initialization; if the user resizes the browser window mid-session, the radii won't update. This is acceptable for the workshop use case where the device orientation doesn't change during a demo.

### Why a small tap-hint `<p>` instead of overlaying text on the chart
The chart already has many labels (band labels, tariff blocks, callout boxes). Adding overlay text would compete for space. A subtle `<p>` below the chart echoes the existing `hero-copy` muted style and doesn't interfere with the chart rendering.

### Why prev/next buttons always visible
The plan offered a choice between "always visible" and "hidden until first chart interaction." Always visible is better for:
- Discovery — users find the nav without having to first successfully tap the chart
- Accessibility — keyboard users can navigate hours without simulating a chart click
- Predictability — the nav doesn't appear/disappear based on hidden state

### Why `aria-label` on the nav buttons
The visible text is "← Prev hour" which is self-describing on desktop. On mobile/screen readers, `aria-label="Previous hour"` / `"Next hour"` provides explicit semantics.

### Why `.hour-nav-label` is a `<span>` not a `<div>`
It's a text content element, not a block container. `<span>` is the semantic choice.

## Risk Assessment
- **RISK-02-01** (larger point radii overlap on narrow mobile charts) — mitigated: narrow viewport uses 3px (vs 4px desktop). 24 points × 3px = 72px of points in ~300px chart width = comfortable spacing.
- **RISK-02-02** (prev/next buttons survive `renderAppShell()` re-creation) — not an issue: `renderAppShell()` runs only once at init, and the buttons are inside the shell.
