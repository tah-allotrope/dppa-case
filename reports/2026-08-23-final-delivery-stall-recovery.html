01 / Executive Summary

Executive Summary

What was found

A brainstorm pass on 2026-08-22 found the repository's delivery pipeline stalled at all three stages at once: a large, competent UI redesign sat uncommitted; three commits (including the one that added the CI formatting gate) had never been pushed; and the production app had been 28 days and 14 commits stale, silently serving a broken service-worker registration the whole time. The guard built to catch exactly this had reported green for three consecutive Mondays because its CI job never had Node installed.

What was done

A six-phase recovery plan executed the same day: stabilise and ship the redesign, build the missing "did this reach anyone" guard class, freeze the translation surface before a translator is engaged, convert five silently-passing checks into real gates, make the Python deck pipeline installable and CI-verified, and fix what the app teaches by default. Every phase is committed, pushed, green in CI, and — where it touched the live app or deck — deployed and verified against production.

02 / Background & Objective

Background & Objective

dppa-case is two linked projects sharing one dataset: a Vite/vanilla-JS teaching app (app/, deployed to dppa-case.web.app) that models Vietnam's virtual-DPPA settlement mechanics, and a set of Python scripts that build a PowerPoint teaching deck, worksheets, and figures from the same settlement engine. The project exists to prepare a presenter for an October 2026 teaching session — the app is the live demo aid, the deck is the walkthrough, and a settlement-engine → JSON-export → deck pipeline exists specifically so no number on a slide can silently disagree with what the engine computes.

A prior session's brainstorm (2026-08-22) found that pipeline's propagation — not its numbers — had quietly broken: work was being produced but not reaching either GitHub or the audience, and several of the guards meant to catch that class of failure had never actually been exercised. The objective of this effort was to close every one of those gaps in one pass, verify each fix against the real repository and the live site rather than in the abstract, and leave the pipeline in a state where the next stall would be caught by a machine within a week instead of by the next manual audit.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding-default assumptions applied

  • ASM-001: the uncommitted working-tree changes were deliberate, wanted work — fixed rather than reverted.
  • ASM-003: the deploy step only proceeds if Firebase credentials are already authenticated in the environment (they were).
  • ASM-004: the self-hosted webfont uses @fontsource/inter with a specific subset list, chosen for parity with the removed fonts.googleapis.com link.
  • ASM-005: strikeEscalation defaults to 2.0%/yr — explicitly not a sourced figure, chosen only so the escalation differential the app teaches is non-zero and a crossover exists inside the horizon.

Constraints honored throughout

  • No translation was invented, machine-translated, or guessed — every UNTRANSLATED sentinel stays until a qualified human replaces it.
  • Every headline-figure change (the gate-sweep pass count) was retired in the same commit that changed it, per the repository's own integrity rule.
  • Deploys and pushes were treated as outward-facing, confirmable actions — verified against the live site and CI after each one, not assumed.
05 / Methodology

Methodology

Each phase followed the same discipline: make the change, run the full local gate set (lint, Prettier, unit tests, coverage, the Python guard suite), run the functional e2e suite, push, and watch the resulting GitHub Actions run to completion rather than assuming success. Two defects were caught this way that inline reading would have missed — a USD-currency display bug in the redesigned chart, and a URL-state regression that silently stripped ?teach=1/?test=1 before the modules that read them could see it, found only because 6 of 60 e2e tests failed and were run down to a root cause rather than retried. One flaky test (a documented browser-launch race under parallel CI workers, unrelated to this session's changes) was confirmed as a flake by isolated re-run before being addressed with a scoped CI-only retry, not by re-running until green.

Where a figure changed (the gate-sweep pass count), the fix was verified three ways before being called done: the settlement-engine export was re-run and diffed against the prior committed JSON, the full deck-rebuild pipeline was executed end to end, and a repository-wide search confirmed no stale copy of the superseded figure survived anywhere the retirement guard scans — including inside the guard's own test fixtures, which had hard-coded the old figure as a "current, not yet retired" example and needed updating in the same pass.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Stabilise and commit done

The uncommitted redesign (direct chart labels, a vertical net-first cancellation breakdown replacing the horizontal strikethrough equation that lost the room in July) had a real bug: the USD strike-reference line silently failed to draw because a currency field had been dropped from shared chart state. Fixed, plus a render-blocking Google Fonts link was replaced with a self-hosted, service-worker-cached font, and the coverage denominator — previously blind to 42% of the app's JavaScript — was corrected and re-baselined honestly (49/49/51/49, with a per-file floor on the settlement engine).

Phase 2 — Propagation guard & deploy done

Built tools/check_delivery_pipeline.py — the guard class the repository lacked: every other check asks "is this number right", this one asks "did the work reach anyone." Made the Monday deploy-freshness job able to fail (it had never had Node installed, so a build failure silently reported green for three weeks). Pushed 20 days of backlog, deployed, and verified the offline drill against the live URL: the service worker activates and a reload while offline still renders the full app.

Phase 3 — Freeze the translation surface done

Froze the 151-key English string table before a translator is engaged (H2, then 2 days out), added a CI check that fails if the frozen key set drifts, converted two figure-embedding deck-text entries to a placeholder-slot contract so a translator never types a number, made number formatting locale-aware, and fixed a Vietnamese worksheet where the loss-factor coefficients were typeset in the wrong numeral convention — a 1000× misreading risk on the two most confusable numbers in the whole settlement.

Phase 4 — Convert silent passes to real gates done

Extended the deck-number verifier to scan speaker notes (the numbers a presenter says out loud), not just slide bodies — reconciled figures roughly doubled. Deleted a dead numeric-reconciliation loop that discarded every mismatch it found. Widened two guards' scan surface to include the shipped app and the hand-maintained terminology map. Built a plan-status checker that found one plan mislabeled "complete" with 0 of 80 tasks done, and four more genuinely done but never marked so — corrected both directions.

Phase 5 — Installable, CI-verified deck pipeline done

Added a pinned requirements.txt for the Python deck/visual builders, a text-level deck comparator (binary PowerPoint diffing is useless — timestamps churn even with no visible change), and a deck-build CI job that rebuilds the deck to a scratch directory and confirms it's identical to the committed one. One real bug surfaced and fixed in CI itself: the builder's --out path didn't create its target directory on a fresh runner.

Phase 6 — Fix what the app teaches by default done

The app's landing scenario is now the canonical teaching case (S1 Matched) instead of a synthetic curve that appears nowhere else in the material, with a non-zero escalation differential so the mission's core claim is visible on first load — plus a one-click "Locked strike" preset and a differential pill, using string keys that had sat unused since an earlier phase. The gate-sweep grid was extended so its headline figure — the strike axis previously stopped exactly at the investor threshold — no longer looks like an artifact of where the chart was cropped: 15 of 70 now clear all three gates, up from 5 of 56, with the full per-gate breakdown published alongside it.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the repository had a well-developed guard system for content correctness and none for propagation. Every check that existed asked whether a number was right; none asked whether finished work had reached GitHub or the audience. That blind spot is what let a 28-day-stale deploy and a 20-day unpushed backlog accumulate without any alert firing. tools/check_delivery_pipeline.py closes it, and is now the highest-leverage single file added this session.

Finding 2 — several existing guards had degraded into checks that could not fail for the reason they existed. The Monday deploy-freshness job had no Node installed, so a build failure always reported "UNKNOWN" and exited 0 — three consecutive Mondays of false-green while the site was genuinely stale. A numeric-reconciliation loop in the deck auditor discarded every mismatch it found rather than reporting it. Both are now real gates; the general pattern (a check that was built in good faith and then quietly stopped carrying information) is worth a standing habit of auditing, not just this one pass.

Finding 3 — the gate-sweep headline was sensitive to an unexamined chart-axis choice. The old strike grid stopped at exactly the investor bankability threshold, so every passing scenario sat in the single edge column — "5 of 56" was a property of where the axis was cropped, not a finding about DPPA economics. Extending the grid two steps past the threshold more than doubled the combined pass rate and is now defensible against exactly the question a lender in the room would ask.

Recommendation: treat the propagation guard as a permanent addition to the Monday job, keep the plan-status checker running so "what's left" stays answerable by a machine, and prioritize engaging the translator (H2) and confirming the session date (H1) — both are now the binding constraints on the calendar, not anything left uncovered by this session's code.

09 / Risks / Open Questions

Risks / Open Questions

Open risks

  • Calendar pressure: H1 (session date) is overdue and H2 (translator) is due in 2 days; every other date in the plan is backward-planned from these two.
  • Lender/investor gate proxies remain illustrative (flat per-kWh floors, not modelled debt schedules or equity IRR) until H3 lands — the deck now states this caveat explicitly in the M5 speaker notes, but the underlying model is unchanged.
  • Coverage floor is honest but still low (49% branches repository-wide) — the re-baseline fixed the measurement, not the coverage itself; raising it is future work, not a regression from this session.
  • .git is 152 MB, dominated by repeatedly-committed PowerPoint binaries — not urgent before October, but worth a decision (Git LFS, or committing the deck only at tagged milestones) before vi/zh builds triple the count.

Open questions for the presenter

  • Is 2026-10-01 still the working session date, or has H1 resolved to something else?
  • Is the 2%/yr strike-escalation default (ASM-005, explicitly unsourced) acceptable as the teaching illustration, or is there a real negotiated index to use instead?
  • Should the lender/investor gate thresholds be recalibrated with real Allotrope deal data before the freeze, or is the illustrative band acceptable for October with the caveat now in the speaker notes?
